# Building FastAPI for Rust: compile-time DX at zero runtime cost

*A technical deep-dive into how `fastrs` brings FastAPI-style ergonomics to Rust without paying the runtime price.*

---

## The Problem

If you have written production APIs in Python, you know how good FastAPI feels. You declare a Pydantic model, annotate your function with a decorator, and you get validation, serialization, and interactive Swagger documentation in one motion. That's genuinely excellent developer experience.

Rust frameworks like Axum and Actix are blazingly fast. They have robust ecosystems and strong correctness guarantees. But writing a simple CRUD endpoint in Axum requires manually wiring request deserialization, field validation, error mapping, and OpenAPI annotations — typically as three or four separate steps that FastAPI collapses into one.

The tradeoff isn't free on the Python side either. FastAPI's magic comes from runtime reflection: Pydantic inspects your model's type annotations when the server starts, and validates every incoming request by walking a dynamically constructed schema tree. You're also running a Python interpreter on every request. That's a real cost — measurable in latency and in money for busy services.

The question we wanted to answer: can Rust get the same ergonomics without the runtime tax?

---

## The Approach

The answer is proc macros — Rust's compile-time code generation system. They let you write code that runs at compile time, reads your source code's structure, and generates new code before the binary is built.

`fastrs` uses two key macros:

**`#[derive(OpenApi)]`** reads struct fields and their `#[validate(...)]` attributes at compile time. It generates an `OpenApiType` implementation that produces the struct's OpenAPI schema as a plain Rust data structure baked into the binary. There is nothing to compute at request time — the schema is a constant, effectively.

**`#[post("/path")]`** (and `#[get]`, `#[put]`, etc.) wraps your handler function and generates Axum route registration code. It inspects parameter types at compile time, infers which ones are path parameters, query params, or request bodies, and wires their OpenAPI contributions into the operation description. The result is a `RouteDef` struct that `App::route()` consumes at startup.

The crucial insight is where validation happens. When you use `Json<T>` as a handler parameter, `fastrs` implements Axum's `FromRequest` trait to deserialize the body and then immediately call `T::validate()` — all inside the extractor. Invalid input never reaches your handler body. The 422 response is generated and returned before your business logic runs. Zero runtime reflection; the validator was generated by the `Validate` derive macro at compile time.

This mirrors what FastAPI does conceptually but executes entirely in compiled, native code.

## Walkthrough: The CreateUser Example

Here is the canonical `fastrs` example:

```rust
use fastrs::{post, Json, Created, OpenApi};
use serde::{Deserialize, Serialize};
use validator::Validate;

#[derive(Deserialize, Validate, OpenApi)]
struct CreateUser {
    #[validate(email)]
    email: String,
    #[validate(length(min = 8))]
    password: String,
}

#[derive(Serialize, OpenApi)]
struct UserResponse {
    id: u64,
    email: String,
}

#[post("/users")]
async fn create_user(body: Json<CreateUser>) -> Created<Json<UserResponse>> {
    Created(Json(UserResponse { id: 1, email: body.email.clone() }))
}
```

**Step 1: `#[derive(OpenApi)]` on `CreateUser`**

At compile time, the `OpenApi` proc macro reads each field and its attributes. It sees `#[validate(email)]` on `email` and emits schema JSON with `"format": "email"`. It sees `#[validate(length(min = 8))]` on `password` and emits `"minLength": 8`. No runtime inspection — this is Rust code generated before your binary exists.

**Step 2: `#[post("/users")]` on the handler**

The macro inspects the function signature. It finds `body: Json<CreateUser>` and knows to call `<Json<CreateUser> as OpenApiExtractor>::modify_operation()` — which sets the request body schema to the one `CreateUser` generated. The return type `Created<Json<UserResponse>>` triggers `<Created<Json<UserResponse>> as OpenApiResponder>::modify_operation()` — which documents a 201 response with the `UserResponse` schema. All of this runs at compile time; the result is a `RouteDef` with a fully formed `Operation` object.

**Step 3: What happens at runtime**

When a request arrives at `POST /users`, Axum dispatches it to your handler. The `Json<CreateUser>` extractor runs first: it deserializes the body from JSON, then calls `body.validate()`. If validation fails — say, the email is missing the `@` sign — the extractor returns a 422 response immediately, with a structured JSON body listing the failing fields:

```json
{
  "errors": [
    { "field": "email", "message": "validation failed: email" }
  ]
}
```

Your handler function never runs.

**Step 4: Where does `/docs` come from?**

At server startup, `App::serve_docs_at("/docs")` serializes the `OpenApi` struct that was assembled during `App::route()` calls. The struct was populated entirely from the compile-time operation objects — no startup scan, no reflection. The JSON is served statically, and Swagger UI renders it into the interactive docs page.

## What's Been Built

`fastrs` has gone through three major versions since the first commit.

**v1** established the core: the `OpenApi` derive macro, the `#[get]`/`#[post]` route macros, the `Json<T>` extractor with automatic validation, `ApiError` for structured error responses, and automatic Swagger UI generation.

**v2** expanded the surface: `Bearer<T>` auth extractor with a pluggable `AuthVerifier` trait, the `Page` pagination extractor with bounds validation, `Created<T>` and `NoContent` response wrappers, `Query<T>` with validation, route nesting with merged OpenAPI paths, and `Header<T>` for typed header extraction.

**v3** added production features: a generic `App::layer<L>()` escape hatch exposing the full Tower middleware stack, HTMX integration behind an optional feature flag with `HxRequest`/`HxTarget`/`HxTrigger` extractors and `HxRedirect`/`HxRefresh` responders, a full Postgres CRUD example, rate limiting via `rate_rs`, simple and custom health check endpoints, UUID-based request ID middleware, `Multipart` form-data extraction, and graceful shutdown on SIGINT/SIGTERM.

The project has 12 GitHub stars, is published on crates.io, and ships a full mdBook documentation site with 46 pages covering every feature.

---

## What's Next

**v4** targets dependency injection — the Rust equivalent of FastAPI's `Depends()`. This is the last major piece toward genuine parity: composable, type-safe dependencies that can be shared across handlers without threading state through every function signature.

Beyond dependency injection, the roadmap includes response model filtering (return only certain fields from a larger struct), background tasks (fire-and-forget work triggered by handlers), and a built-in test client for handler-level testing without spawning a server.

The parity roadmap is public in the repository. Contributions welcome.
